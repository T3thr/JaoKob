## 6. Migration, rollback, assumptions and follow-up

- Supported chain: **format1/content2.0→format1/content2.1→format2/content2.1**. Source and target schema/causal state validate at their boundaries; no widening of the old presentation migration to rewritten text.
- The actual legacy historical flag is `keepsake.lily_fragment` (conceptual `hasLeaf` in the directive). True independently maps each payload/checkpoint to held/acquired/remembered `item_leaf`; false maps empty. Other items/refusals/secrets are not retroactively awarded. The pure helper understands an unambiguous literal alias, but the published Save1 identifier grammar/production catalog still governs admitted records.
- Recovery and Resume never write. A later accepted normal action stages/reads/backs up/promotes Save2; original canonical bytes become backup. Quota/backup/race/future/corrupt/unknown records do not grant overwrite authority. Digest-bearing legacy input remains protected until verification/recomputation support exists. An unavailable save continues in memory with visible notice rather than claiming durability.
- Rollback keeps dual-format admission/downgrade/write guards or disables writes. Do not downgrade Save2, delete raw backup or recover an invalid inventory by replacing it with an empty one. Reverting visual code cannot reverse an accepted item decision.
- Remaining tasks: T6 Log; T7 approved new prose/item/secret IDs and baseline callback conjuncts; T8 later-act/fair ending map; T9 expanded original art/registry; T10 content3/variant/vignette mapping and integration; T11 final human/device/performance acceptance. Physical item callbacks must use held membership, with equally complete remembered/absent variants. Current consuming `use` has no active new story opportunity; non-consuming utility needs an explicit authored contract.
